# Spotter AI — Project Overview & How It Works

A plain-language guide to the whole system, written from the actual code in
this repository (backend routes, frontend screens, ML pipelines). If you can
read this file, you understand what Spotter AI does, which parts are real
data, which parts are model predictions, and which parts are demo/synthetic —
without reading any code.

**The one-sentence summary:** Spotter AI is a manganese mine-planning demo
for the Balaghat belt (MP, India) that maps where manganese ore is likely to
be (reserve model), predicts how much the mine will produce (production
model), detects when production will fall short and why (SHAP), and
recommends moving equipment between zones to recover the shortfall
(OR-Tools optimization) — all wrapped in a chat assistant that answers
questions in plain language using the same models.

  it.
- Schema: 15 tables (zones, geological, geochemical, exploration, satellite,
  weather, production, equipment, equipment_status_history, blasting,
  mining_schedule, zone_terrain_access, data_source_metadata,

### ML / AI (Python)

| Model / library | Where it is used | What it powers |
| --- | --- | --- |
| scikit-learn **RandomForestClassifier** | `ml/pipelines/reserve_model/` (deployed artifact is random_forest) | Zone prospectivity % (Phase 12) |
| **XGBClassifier** | same pipeline (compared, RF won the CV) | candidate prospectivity model |
| scikit-learn **RandomForestRegressor** | `ml/pipelines/production_model/` (deployed artifact) | Production prediction tonnes (Phase 15) |
| **XGBRegressor / GradientBoostingRegressor** | same pipeline (compared, RF won held-out RMSE) | production model candidates |
| **SHAP** (TreeExplainer) | `ml/pipelines/production_model/explain.py` | Shortfall cause attribution % (Phase 17) |
| **OR-Tools CP-SAT** | `ml/pipelines/optimization/or_tools_model.py` | Schedule constraint validation / feasibility (Phase 18) |
| Rule-based multi-criteria ranking | `ml/pipelines/optimization/zone_comparator.py` | Candidate zone ranking (Phase 19) — weights + `objective.score_schedule` |
| Linear regression (np.polyfit) | `ml/pipelines/resource_estimation/estimate.py` | Ore thickness calibration for sparse zones (Phase 13) |
| Anthropic API (optional) | `backend/app/services/assistant_service.py` | Chat assistant LLM (tool-use classification + phrasing). Optional: `LLM_API_KEY` in `.env`; **without a key the assistant runs a deterministic grounded fallback** that answers from the same real tool results. |

### External data services wired up

| Service | What it fetches | Status |
| --- | --- | --- |
| Microsoft Planetary Computer STAC API | Real Sentinel-2 NDVI + band ratios for the AOI | Wired (`satellite_real.py`) but **network-fetch fails in practice here** — seeds fall back to synthetic NDVI; the fallback path is what populates the DB |
| IMD gridded rainfall via `imdlib` | Real daily rainfall for the AOI | Wired (`weather_real.py`); the seed run in this environment reported a fetch failure and used the synthetic fallback |
| Anthropic API | LLM tool-use for the assistant | Optional; off unless `LLM_API_KEY` is set |

Everything else (geology, geochemistry, drilling, equipment, blasting,
production history, terrain) is **synthetic data** generated by fixed-seed
generators in `backend/app/services/synthetic/` and seeded into Supabase.

## SECTION 3 — SCREEN-BY-SCREEN FLOW

All screens fetch via `src/services/api.js`, which calls
`http://localhost:8000` (or `VITE_API_BASE_URL`) and attaches the
`X-API-Key` header on POSTs. Every GET returns the raw backend payload; no
frontend caching.

### Shared UI behavior (all screens)

- While data loads: skeleton loaders (`Skeleton`).
- If the backend is unreachable: an error card with a Retry button.
- The top nav (Layout) has 8 links: Overview, Reserve Map, Production, Risk
  Analysis, Schedule, Recommendations, Assistant, Metrics.

---

### 1. Overview (`/overview`)

**On load — 4 parallel GETs:**
1. `GET /api/v1/reserve/prospectivity` — runs the trained RandomForest
   classifier over all 20 zones → per-zone prospectivity %.
2. `GET /api/v1/production/predict/current` — runs the production RandomForest
   regressor on the current 30-day schedule → predicted vs target tonnes.
3. `GET /api/v1/production/shortfall/current` — computes shortfall % and the
   PRD §15 risk level (LOW/MEDIUM/HIGH) from the prediction.
4. `GET /api/v1/equipment` — fleet snapshot from the DB (read-only).

**What renders:** four StatCards (Best-zone prospectivity, Production
forecast in kt, Shortfall risk, Equipment availability), a Shortfall Risk
detail card with the block-style ProgressBar, and the Data Confidence widget
(`GET /api/v1/data-confidence`).

**Clickable elements:**
- Each StatCard navigates to another screen (`/reserve-map`, `/production`,
  `/risk-analysis`, `/schedule`) via `window.location.hash`.
- "View risk analysis →" button → `/risk-analysis`.
- **Predicted vs displayed:** prospectivity % and production tonnes are
  **live model predictions**; equipment availability and confidence labels
  are **displayed DB data** (no prediction).

---

### 2. Reserve Map (`/reserve-map`)

**On load — 4 parallel GETs:**
1. `GET /api/v1/zones` — 20 zone polygons as GeoJSON (DB).
2. `GET /api/v1/reserve/prospectivity` — all-zone prospectivity (model).
3. `GET /api/v1/reserve/resource-estimate` — all-zone estimates (Phase 13
   statistical estimation).
4. `GET /api/v1/mineability` — all-zone live mineability scores (weighted
   composite, recomputed per request).

**What renders:** a 4×5 grid of zone cells (A1–D5) colored by prospectivity
(green HIGH ≥70%, yellow MEDIUM 40–70%, grey LOW). Zone B3 is selected by
default.

**Clicking a zone cell** (e.g. **B2**) fires 4 more parallel GETs:
- `GET /api/v1/reserve/prospectivity/B2` — **model prediction** (RF classifier
  output + calibration).
- `GET /api/v1/reserve/resource-estimate/B2` — **statistical estimate**,
  not a learned model (drill-influence volume × density 3.5 t/m³, thickness
  regression for sparse zones).
- `GET /api/v1/zones/B2/drilling` — drill-hole records (DB, raw data).
- `GET /api/v1/zones/B2/geological` — lithology + geochemistry (DB, raw).

The right-hand detail panel updates: prospectivity badge, mineability badge
(from the already-loaded all-zones payload), ore/volume/grade/contained-Mn
table, drill-hole list, geology summary. Zones with no drilling show
"⚠ Limited drilling — no statistical estimate".

**Predicted vs displayed:** prospectivity = model; resource estimate =
deterministic statistical calculation; drilling/geology = stored data.
No WRITE actions on this screen.

### 3. Production (`/production`)

**On load — 5 parallel GETs:**
1. `GET /api/v1/zones` — for the zone filter dropdown.
2. `GET /api/v1/production/history` (+ `?zone_id=` when a zone is selected) —
   historical daily planned vs actual tonnes (DB, **raw stored data**).
3. `GET /api/v1/production/current-target` — the 82,000 t 30-day target
   (computed from the generator constants, read-only).
4. `GET /api/v1/production/predict/current` — **model prediction**.
5. `GET /api/v1/production/shortfall/current` (+ `?zone_id=`) — **derived**
   from the prediction (shortfall tonnes/%, risk level).

**What renders:** four StatCards (Target, Predicted, Shortfall, Risk), a
Shortfall Risk ProgressBar card, a Recharts line chart of planned vs actual
over the last year (with a red "Predicted" marker at the end), and a
per-zone breakdown table.

**Clickable elements:**
- **Zone dropdown** — re-fires the history + shortfall GETs with `?zone_id=`;
  the table and chart re-render per zone. The forecast card stays mine-wide.
- **Table rows** navigate to `/reserve-map`.
- **"View Risk Breakdown →"** → `/risk-analysis`.
- **Predicted vs displayed:** the trend chart is historical raw data; the
  Predicted stat and shortfall are model-derived. No WRITE actions.

---

### 4. Risk Analysis (`/risk-analysis`)

**On load — 4 parallel GETs:**
1. `GET /api/v1/production/shortfall/current` — shortfall + risk level
   (derived from model prediction).
2. `GET /api/v1/production/shortfall/current/explain` — **SHAP** feature
   attribution: runs `explain_prediction` on the averaged schedule features,
   rolls values into PRD categories (Equipment downtime, Rainfall, Blasting
   delays, Ore grade) normalized to 100%.
3. `GET /api/v1/optimization/risks` — risk triggers (weather threshold +
   shortfall) per at-risk equipment (rule-based on live weather + shortfall).
4. `GET /api/v1/weather/risk-alert` — zones flagged over the 60 mm/150 mm
   rainfall thresholds (DB weather rows, threshold rule).

**What renders:** three stat boxes (Predicted, Shortfall, Risk Level), the
PRD §15 block-style risk bar, a horizontal bar list of SHAP contributor
percentages, a Reallocation Risk Triggers table (equipment/zone/reason/
severity), and a Weather Risk Alerts table (zone/date/rainfall/trigger).

**Clickable elements:**
- "View Recommended Actions →" → `/recommendations`.
- **Predicted vs displayed:** shortfall = model-derived; SHAP causes =
  model-derived (explainability); triggers/alerts = rule-based on DB data.
  No WRITE actions.

---

### 5. Schedule (`/schedule`)

**On load — 3 parallel GETs:**
1. `GET /api/v1/schedule/current` — the current 7-day shift schedule
   (DB rows: date/shift/equipment/zone/output/status).
2. `GET /api/v1/equipment` — fleet table (DB).
3. `GET /api/v1/production/predict/current` — model prediction for the
   header summary.

**What renders:** the header prediction line, two buttons, the
Current Assignments table (equipment → zone, availability, planned output;
rows in A1 highlighted red), and a "Next 7 Days — Shift Blocks" table.

**Clickable elements (both are WRITE/action buttons):**
- **"Validate Schedule (PRD §22)"** → `POST /api/v1/optimization/validate-schedule`
  with the current schedule body. Backend runs the pure-Python constraint
  validator **and** the OR-Tools CP-SAT feasibility solve; the card shows a
  pass/fail badge per constraint. **Requires X-API-Key.** Does not change the
  DB (pure validation).
- **"Trigger Recalculation (P21)"** → `POST /api/v1/recalculation/trigger`.
  **This is a WRITE action**: it runs one PRD §24 recalculation cycle
  (risk detect → rank candidates → re-predict → record) and **appends to the
  recalculation audit log** (`recalculation_log` table + JSONL). It can also
  store a pending recommendation in the in-memory Phase 21 registry.
- "View Recommendations →" → `/recommendations`.
- **Predicted vs displayed:** the schedule and equipment tables are raw DB
  data; the header tonnes are a model prediction.

---

### 6. Recommendations (`/recommendations`)

**On load — 3 parallel GETs:**
1. `GET /api/v1/recommendations` — mine-wide scan: for every at-risk unit,
   pick candidate zones (prospectivity ≥40%, haul ≤12 km), rank them with
   the multi-criteria scorer, and compute before/after production + shortfall
   by **re-running the production model** on the hypothetical moved schedule.
   This is the heaviest endpoint (model runs per candidate).
2. `GET /api/v1/production/shortfall/current` — baseline shortfall.
3. `GET /api/v1/demo/state` — whether a recommendation was accepted (reads
   `ml/data/processed/demo_state.json`).

**What renders:** one card per recommendation: "MOVE EX-04 from A1 → C3",
the reason (from the actual risk trigger), three impact boxes
(Production before→after, Shortfall before→after + % reduction, Shortfall %
before→after + status), the full candidate ranking table (zone, total score,
the 5 criteria), and an action area.

**Clickable elements:**
- **"Accept & Apply"** → `POST /api/v1/demo/accept`. **WRITE action**:
  computes the top recommendation and **writes to `demo_state.json`**
  (accepted equipment/from/to/expected_impact, status `approved`, timestamp).
  It does NOT modify the mining_schedule table — the "applied" state is the
  demo-state file, which the Metrics screen reads for the before/after
  impact. Requires X-API-Key.
- **"Reset Demo"** (shown after accept) → `POST /api/v1/demo/reset`.
  **WRITE action**: clears the accepted state in `demo_state.json`
  (restores pre-demo state for repeat runs).
- "Ask Spotter AI About This →" → `/assistant`.
- **Predicted vs displayed:** everything here is model/optimizer-derived —
  the recommendation, the expected impact (two real model predictions), and
  the ranking. The shortfall card is model-derived too.

---

### 7. Assistant (`/assistant`)

**On load:** nothing is fetched — a static welcome bubble and six
suggested-question chips appear.

**Typing a question / clicking a chip** → `POST /api/v1/assistant/chat` with
`{message, conversation_history}` (rolling history of prior user/assistant
turns, capped). Backend flow in `assistant_service.py`:
1. If `LLM_API_KEY` is set: call the Anthropic API with tool-use schemas for
   13 backend functions; the LLM picks which function(s) the question maps
   to (e.g. "why is production falling" → `shortfall_explain`).
2. The backend executes those functions — **the real services/models** (same
   ones the screens call) — and feeds the raw results back to the LLM to
   phrase the answer.
3. If no API key (the current config) **or the LLM call fails**: a
   deterministic fallback classifies intent by keyword and answers from the
   same real tool results. Either way, **the assistant never invents
   numbers** — every figure comes from an actual backend call this turn.

**What renders:** user bubbles on the right, Spotter bubbles on the left; a
"Based on: …" line under each answer (from `data_sources_used`); a typing
indicator while the request runs; an error banner on failure.

**Clickable elements:** the 6 suggestion chips (they auto-send), the text
input + Send button (disabled while loading).
**Predicted vs displayed:** the answer text is LLM/deterministic phrasing;
every fact inside it is a live model/service result. **No WRITE actions**
(the chat only reads; audit lines are appended server-side to
`ml/data/processed/assistant_audit.jsonl`).

---

### 8. Metrics (`/metrics`)

**On load — 1 GET:**
- `GET /api/v1/metrics/summary` — aggregates:
  - Reserve model: Precision/Recall/ROC-AUC parsed from
    `ml/pipelines/reserve_model/evaluation_report.md`.
  - Resource estimation: B3 tonnage/volume vs the PRD reference, % error.
  - Production prediction: MAE/RMSE/MAPE from
    `ml/pipelines/production_model/artifacts/model_metadata.json` +
    `evaluation_report.md`.
  - Shortfall classification: the Phase 16 threshold rule evaluated on the
    historical feature table (accuracy/precision/recall/F1 + risk
    distribution).
  - Scheduling impact: the **live** recommendation's before/after production
    and shortfall (recomputed from the actual Phase 20 model calls).

**What renders:** a disclaimer banner ("Demo/prototype values … NOT claims of
real-world mining performance") and five metric blocks with rows/bars.
**Clickable elements:** none. **All read-only**; the numbers are either
parsed from committed evaluation reports or recomputed live from the models.

## SECTION 5 — WHAT'S REAL VS WHAT'S SYNTHETIC/MOCKED

**Be honest up front:** this is a hackathon MVP. Nearly all domain data is
synthetic by design (documented in `docs/synthetic_data_assumptions.md`); the
"real" parts are the models (trained on that synthetic data), the live
predictions, and the actual database/API wiring.

### Live in Supabase (real rows, inserted by seed scripts)
- All 15 tables are real PostgreSQL/PostGIS tables in your Supabase project,
  populated by the idempotent seed scripts (`seed_grid`, `seed_data_sources`,
  … `seed_terrain`, plus the demo weather trigger). The data *inside* them is
  generated by the fixed-seed synthetic generators — real rows, synthetic
  values.

### Real external data attempted (but currently falling back)
- **Satellite NDVI**: a real Sentinel-2 fetch via Planetary Computer is
  wired in `satellite_real.py`, but in this environment the fetch fails, so
  the seed used `--no-real` / fell back to synthetic NDVI.
- **IMD rainfall**: a real fetch is wired in `weather_real.py`; the seed run
  reported a fetch failure and used the synthetic demo-trigger weather
  (A1 = 110 mm spike, which is the demo's driving event).

### Real ML predictions (computed live, not stored)
- Prospectivity % — RandomForest classifier (trained artifact).
- Production tonnes (current + hypothetical moves) — RandomForest regressor.
- Shortfall tonnes/% and risk level — derived from the model prediction with
  the PRD §15 thresholds.
- SHAP cause attribution % — TreeExplainer on the production model.
- Mineability score — weighted composite (partly live weather/equipment,
  partly static features).
- Resource estimates — deterministic statistical calculation, not a learned
  model.
- Recommendation impact (before/after) — two real model runs.
- Metrics — parsed from committed evaluation reports + live recomputation.

### Pure display of stored data (no prediction)
- Historical production chart (planned vs actual).
- Schedule tables, equipment fleet, drill holes, geology/geochemistry,
  terrain, weather time series, data-confidence registry.

### Placeholder / not fully wired (be aware)
- **Satellite/IMD real feeds**: the ingestion code exists but the live
  fetches currently fail on this network; the synthetic fallback is what you
  see in the DB.
- **Anthropic LLM**: optional and currently **off** (no `LLM_API_KEY`) — the
  assistant's deterministic grounded fallback answers every question. Set the
  key in `backend/.env` to enable LLM phrasing (the grounding guardrails are
  identical either way).
- **OR-Tools**: the CP-SAT solver is used for schedule *validation* (the
  Validate button). The *recommendation ranking* is the rule-based
  multi-criteria scorer, not the CP-SAT optimizer — the CP-SAT objective is
  documented as scaffolding (Phase 18–20 scope decision).
- **Demo "Apply"**: Accept & Apply updates a demo-state file, not the live
  mining_schedule table — a documented prototype simplification so the demo
  is repeatable.
- **Map**: the Reserve Map is a CSS grid, not a real GIS map library
  (no Leaflet/MapLibre dependency exists).

## SECTION 6 — HOW TO RUN THIS PROJECT LOCALLY

Prerequisites: Python 3.11+ and Node.js 18+ on the machine, a free Supabase
project with PostGIS enabled, and the project URI from
Supabase → Project Settings → Database → Connection string.

```bash
# 1. Backend env — one-time
cd backend
cp .env.example .env          # paste your Supabase DATABASE_URL into .env
python -m venv .venv
.venv\Scripts\activate        # Windows  /  source .venv/bin/activate
pip install -r requirements.txt

# 2. Migrate + seed the Supabase database (one-time; idempotent)
cd ../database
alembic upgrade head          # reads DATABASE_URL from backend/.env
cd ../backend
python -m app.core.seed_grid
python -m app.core.seed_data_sources
python -m app.core.seed_geological_geochemical
python -m app.core.seed_drilling
python -m app.core.seed_satellite --no-real   # real fetch may fail → synthetic
python -m app.core.seed_weather
python -m app.core.seed_equipment_blasting
python -m app.core.seed_production_schedule
python -m app.core.seed_terrain
python -m app.core.seed_weather --demo-only    # A1 110 mm rainfall spike

# 3. Start the backend
uvicorn app.main:app --reload        # http://localhost:8000
# sanity: curl http://localhost:8000/health
#   → {"status":"ok", ..., "db_connected": true, "postgis_available": true}

# 4. Start the frontend (separate terminal)
cd ../frontend
npm install
npm run dev                         # http://localhost:5173
```

Notes:
- Model artifacts (the trained `.joblib` files) are already present under
  `ml/pipelines/*/artifacts/`; they load lazily on the first prediction.
  To retrain: `cd ml/pipelines/reserve_model && python train.py` (same for
  `production_model`).
- Mutating endpoints (Validate, Recalculation, Accept/Reset) require the
  header `X-API-Key: spotter-demo` (env-configurable) — the frontend sends
  it automatically via `services/api.js`.
- After a demo run, restore the pre-demo state with
  `python -m app.core.reset_demo_scenario` (from `backend/`).
- Full details: `docs/DEPLOYMENT.md` (setup) and `docs/DEMO_SCRIPT.md`
  (the 12-step presentation walkthrough).
